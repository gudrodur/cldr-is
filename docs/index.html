Sorting is the one no polyfill can fix

á é í ó ú ý ð þ æ ö are letters in their own right in Icelandic, not accented variants. A fallback collation treats them as variants, so Ævar lands near the top instead of second-to-last and Þórður sorts among the T’s. There is no Intl.Collator polyfill — formatjs does not ship one — so unlike dates and numbers, this cannot be fixed by loading data.

      The trap next door: date pickers don’t use Intl

      A polyfill fixes Intl. It does not fix a library that never used it. react-day-picker — and therefore every shadcn/ui calendar — localises through date-fns, so a fully polyfilled page still renders October 2026 and Su Mo Tu We Th Fr Sa until you pass a locale: 

      import { is } from "date-fns/locale/is";
<DayPicker locale={is} />   // október, Má Þr Mi Fi Fö La Su, Monday-first

      And once you do, check what you render beside it: date-fns’s abbreviated Icelandic months are not CLDR’s. Six of twelve differ.

      SourceAbbreviated months
      date-fnsjan. feb. mars apríl maí júní júlí ágúst sept. okt. nóv. des.
      CLDRjan. feb. mar. apr. maí jún. júl. ágú. sep. okt. nóv. des.

      What to do about it

      On the server: load the data

      Cloudflare Workers embeds the same trimmed ICU, so a server-rendered page has the gap too. There the polyfill earns its size — loaded once per isolate, not per visitor, and it fixes every locale at once. 

      import "intl-is/server";   // first import in the worker entry

      It must be formatjs’s polyfill-force, not polyfill: the runtime has an Intl.DateTimeFormat, it just answers in English, so the conditional polyfill decides nothing is wrong. And polyfill-force replaces the global for every locale — load data for all the languages you serve, or they regress.

      In the browser: format it yourself

      We shipped the browser polyfill behind a flag, measured it, and turned it off. It is 191,966 B gzip, most of it a time-zone table, against 1,618 B for manual formatters that also cover sorting. Copy them or import them — both are fine: 

      import { formatIsDate, formatIsNumber } from "intl-is/format";
import { compareIs } from "intl-is/collate";

      Then pin whatever you write to Node

      This is the part that matters more than the code. The browser you are developing in cannot tell you whether your Icelandic is right — it is the broken one. Node still has the data, so Node is the oracle: 

      expect(formatIsDate(d)).toBe(d.toLocaleDateString("is-IS", { …options }));

      Write that once per shape and your hand-written month table stops being a guess. Two ways to get the test itself wrong: do not pin timeZone: "UTC" on the Intl side unless your call site passes one (it makes the equality true by construction — it hid a real bug from us for a review round), and run the suite in more than one time zone.

      Is this ever going to be fixed upstream?

      Plan as if not. workerd#64 has been open since 2022; the maintainer was receptive and the reporter measured the full-ICU embed at 63 MB → 82 MB, then it went quiet — no comment, no label, no assignee for over 1,400 days. Chromium’s exclusion is policy keyed to whether Chrome’s own UI is translated into the language, which Icelandic is not. Mozilla considered the same trim for Firefox (bug 1612379) and declined on principle — which is exactly why the checks above pass in Firefox and fail in Chrome. Two vendors, the same 1–2 MB, opposite calls. That is a values split, and it does not resolve by filing a bug.
